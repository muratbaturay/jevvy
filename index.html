    01 · The Control Plane

    Separate judgment from execution

    One loop, two jobs. Decide cheap. Generate when it counts.

    Two layers, one gate

    Decision layer · Jev

    • Answers bounded questionsYes or no. One of five. A score from 0 to 1. Questions with an answer space you wrote down in advance.
    • Returns a typed answer with a probabilityNot a paragraph that happens to contain a verdict. A value your code can branch on, and a number saying how sure.
    • Flags low confidenceUnder your threshold it says so instead of bluffing. That is what calibration is for.
    • Never writes textNo prose, no summaries, no explanations. If the job is to write, it is not this layer's job.

    Policy
    gate

    • Threshold per decision type
    • Allowed tools and scope
    • Below threshold: fall back to Claude

    Execution layer · Claude Code

    • Reads the repositoryFinds the files, understands the code, builds the context the decision was made from.
    • Generates the review, the fix, the docUnbounded output is what a language model is for. This part never moves.
    • Runs tools and testsExecutes commands, linters, and test suites, and captures what came back.
    • Returns the changed artifactA diff, an updated file, a report. Something a verifier can inspect.

    From request to verified result

    The classifier answers. The gate authorizes. The tool executes.

    • Jev answers what you asked
    • The gate decides what's allowed
    • Claude Code does it within bounds

    Why the split pays, and where it doesn't

    The three chapters are the pattern. These pages are the argument behind chapter 01, condensed from the source article and checked against what TypeSafe has published.

    Part 01

    Two jobs, one tool

    Every agent you build with Claude Code does two different jobs with the same model. The first is generation: write the function, draft the reply, summarise the thread. The output space is unbounded, so it needs a language model. The second is decision: did the tests pass, should this merge, is this ticket urgent. The output space is bounded and typed. Yes or no. One of five. A number between 0 and 1.

    Today both jobs go through the generative model. Ask Claude whether a diff passes review and it writes a paragraph that happens to end in a verdict. You pay generation prices and generation latency for what is structurally a classification.

    Jev, from TypeSafe AI, was built for the second job only. You hand it state (a diff, a log, a transcript) and a list of typed questions. It returns an answer to each, with a calibrated probability, in one round trip. It generates nothing. TypeSafe calls the training method RLCD, reinforcement learning for calibrated decisions: the objective is to be right and to know how sure to be, rather than to sound right.

    Latency per call
    70 to 500 ms, against 3 to 329 s for chat models reasoning their way to the same classification
    Price
    $0.042 per million input tokens; output tokens free, because there are none
    Provenance
    TypeSafe's own figures, not independently verified; access is waitlist-only as of September 2026

    Part 02

    Where the multiplier comes from

    The 20 to 200x figure is not one Jev call racing one Claude call. It comes from decision density. Inside a real loop most model calls are checks: did that step succeed, is this the right file, does the output satisfy the constraint, retry or escalate. The source article's author counted 31 bounded checks in a single session that fixed a 340-line auth module. Each one went through the full model, which reasoned in prose and then concluded, for a question with two or three valid answers.

    Move those 31 checks to a classifier and you have not made one call faster. You have removed 31 generation calls and replaced them with 31 calls that return in under half a second for a fraction of a cent. The gain compounds at every decision point. A loop that is mostly generation, such as writing a long document, gets almost nothing, because there is nothing to offload.

    Part 03

    Three steps to wire it in

    1. Audit the decision points

    Take a real transcript, not an imagined one, and mark every place the model was asked a bounded question. Five lines per point:

    templateLocation:      where in the loop
Question:      as asked, verbatim
Answer space:  bounded or unbounded
Current cost:  tokens, seconds
Candidate:     yes or no

    In loops with a review or validation step, expect 25 to 40% of calls to be decisions in a generation costume.

    2. Define the typed schema

    Give Jev the context and a list of typed questions. Every question is scored in the same round trip, so three questions cost one call, not three.

    illustrativecontext:   <raw test output>
questions:
  - id: tests_pass        type: boolean
  - id: failure_kind      type: one-of [flake, related, environment, none]
  - id: confidence        type: score 0..1

    3. Route inside the loop

    At each decision point, insert a router instead of a call to the generative model.

    illustrativedecide(question, context):
  if question is a judgment call:   return claude.decide(context)
  answer = jev.ask(context, question.schema)
  if answer.probability >= threshold[question.id]:
      return answer.value
  return claude.decide(context)      # fall back below threshold

    The fallback line matters more than it looks. Part 07 is about it.

    Part 04

    A worked loop: review, decide, fix, rerun

    An agent reviews a pull request, decides whether it needs changes, fixes it, reruns the tests, and decides what to do next. Figures are the source article's estimates for one PR.

    Before and after moving the three decisions to Jev
    StepBeforeAfter
    1 · Review the diffClaude generates, ~1,400 tokens, ~11 sunchanged
    2 · Verdict: approve, change, escalateClaude generates, ~600 tokens, ~5 sJev, ~0.3 s

    The review and the fix stayed on Claude. Only the classification weight moved. On a team pushing 40 to 60 PRs a day through a loop like this, that is the difference between an agent that feels slow in CI and one that answers before you have switched tabs.

    Part 05

    Where the ceiling is real

    The top of the range shows up in one narrow band: high frequency, low ambiguity, tightly bounded decisions, run at volume.

    • Triage queues. Urgent, standard, or spam, thousands of times a day.
    • CI gating. Pass, fail, or flaky, on every commit across a large repository.
    • Policy filters. Does this output break a fixed rule, checked before every generation ships.
    • Handoff routing. Which of five specialist agents takes this task, at the top of every workflow.

    In each, the schema barely changes and a wrong answer is cheap enough that a threshold plus a fallback catches the edge cases. Outside that band, expect the bottom of the range.

    Part 06

    Where forcing it backfires

    Jev cannot hallucinate free text, because it never writes any. It can absolutely pick the wrong option inside a valid schema. If your categories overlap or your context is thin, it still returns a confident, clean-looking answer, because that is what it is built to do. A broken schema does not raise an error. It produces a wrong answer that looks exactly like a right one.

    The source article's author learned this on a content pipeline: four categories along the lines of "high priority", "urgent", "needs review", and "flag" that were not mutually exclusive. The answers were fast, cheap, confident, and internally inconsistent about a third of the time. Fixing the schema cost about six hours of relabelling.

    Do not route these to a classifier:

    • Judgment calls. Is this writing good, is this argument persuasive. No fixed schema captures it.
    • Low-volume, high-stakes decisions. Five times a month does not repay the setup.
    • Anything generative. A classifier bent into a writer is a worse writer.
    • Schemas still changing weekly. Categories you are still discovering are not ready to offload.

    Part 07

    Verification when the failure looks clean

    Because the failure mode is a confident wrong answer rather than an obvious one, the verification layer cannot rely on the output looking wrong. Two mechanisms do the work.

    A threshold per decision type, not one global number. A merge-or-flag decision and a spam-or-not decision have different acceptable error rates. Set each threshold by measuring disagreement against Claude on a sample, not by picking a round number. The source article uses 0.87 as an example for one decision; it is an example, not a rule.

    A shadow check on high-stakes decisions. Even above threshold, send a small share (the article uses 5%) through Claude in parallel, logged rather than blocking, and record disagreements. That is how schema drift shows up as a log line instead of a downstream failure.

    illustrativedecide(question, context):
  answer = jev.ask(context, question.schema)
  if answer.probability < threshold[question.id]:
      return claude.decide(context)
  if question.id in HIGH_STAKES and random() < 0.05:
      shadow = claude.decide(context)          # not blocking
      log_if_different(answer.value, shadow)
  return answer.value

    Chapter 03 says the same thing in one line: confidence is not proof.

    Part 08

    The cost ledger

    The saving is not the whole bill. It is the classification tax you were paying without knowing it was separable. Start from the article's assumptions, then type in your own numbers.

    Part 09

    Five mistakes, and the actual skill

    1. Routing generation to a classifier because it is cheap. It will answer. The answer will be bad.
    2. One global threshold. A misrouted ticket and a merged bad PR are not the same risk.
    3. Skipping the schema audit. Overlapping categories do not error; they drift.
    4. Never sampling for drift. Sure and correct diverge as inputs shift. Without a shadow check, you find out from a failure.
    5. Treating 200x as a target. It describes one band of work. Bending your architecture toward the number means bending it away from your problem.

    None of this makes Jev smarter than Claude Code, and none of it replaces Claude Code. The skill is decomposition: look at a loop you already built and ask, honestly, which parts generate and which parts are classification in a generation costume. The teams getting real multipliers did the audit first and moved only that.

    02 · The Worktree Method

    Same codebase · parallel progress · no collisions

    Four agents, four branches, no shared files. Speed comes from isolation, not headcount.

    Isolate the work before you parallelize it

    The no-collision rules

    1. 01One owner per fileEach file has exactly one responsible worktree. If two tasks need the same file, they are one task.
    2. 02One branch per taskSmall scope, clear intent. A branch that does two things merges twice as slowly.
    3. 03Test before handoffRun the local checks and fix what they find before asking anyone to review.
    4. 04Merge verified diffs onlyOnly changes that passed review and checks enter the queue. The queue is linear on purpose.

    Parallelism without isolation creates rework.

    Collapsed workspaces, conflicting edits, and untested changes slow everyone down.

    More agents only help when the work is isolated.

    03 · The Proof Contract

    No evidence, no done

    Done is a claim. Evidence is what makes it true.

    Every task returns five things

    1. 01ArtifactThe concrete output: the file, the answer, the change.
    2. 02DiffExactly what changed: additions, deletions, modifications, nothing implied.
    3. 03TestsWhat ran and how it went: commands, results, pass or fail.
    4. 04LimitsWhat was not verified: known gaps, assumptions, the untested path.
    5. 05ReceiptHow to reproduce and inspect: paths, URLs, log ids, run ids.
    • Evidence makes reviewers independentA claim needs the claimant. Evidence lets anyone check without extra context.
    • Same standard for every agentFive items, every time. Reviews stay fast because they stay identical.
    • Missing evidence means incompleteIf any item is missing or unclear, the task is not done. Send it back.

    Gate the result with independent verification

    The verifier prompt

    Compare the artifact with the goal.
    Check the evidence.
    Answer VERIFIED, REFUTED, or UNKNOWN.

    Confidence is not proof.

    A calibrated probability says how sure the classifier is, not whether it is right. That is why chapter 01's router keeps a shadow check.

    Trust the receipt, not the claim.
